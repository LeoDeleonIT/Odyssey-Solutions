Microsoft 365 Scan-to-Email: Prepare for the December 2026 Change

Published October 3, 20264-minute readPublished by Odyssey Solutions · Guidance for Greater Houston businesses.

A copier can produce a scanned file while the email carrying it never reaches its destination. For an office that sends signed forms, job documents, or routine reports this way, that creates a small technology failure with a direct effect on daily work.

Houston businesses using Microsoft 365 should identify those sending workflows now. Microsoft's current plan changes the default for SMTP AUTH Basic Authentication at the end of December 2026. The effect on your office depends on how each device or application actually sends email.

What Microsoft has announced

The Exchange Team published its revised timeline on January 27, 2026, and updated the post on January 29. As checked on October 3, it says:

  • Before the end-of-December change, SMTP AUTH Basic Authentication behavior remains unchanged.
  • At the end of December, it will be disabled by default for existing tenants. Administrators will still be able to enable it if needed.
  • For new tenants created after December 2026, it will be unavailable by default, with OAuth the supported authentication method.
  • Microsoft plans to announce the final removal date in the second half of 2027.

December is therefore a default-setting milestone, not a claim that Microsoft has scheduled permanent removal for every existing tenant that month. Use the official Exchange Team timeline when checking a vendor's advice.

Find the workflows people do not think of as email

Ask each department what sends messages without someone opening Outlook. Start with multifunction printers, scan-to-email buttons, scheduled reports, and line-of-business software.

For each workflow, record:

  • Device or application, location, and business owner
  • Sending address and sending service
  • Authentication method, confirmed by IT or the vendor
  • Whether recipients are inside the business, outside it, or both
  • How often it runs and who notices a failed delivery
  • Vendor contact and the next available test window

A familiar Microsoft 365 sender address alone does not tell you which delivery method is in use. SMTP AUTH itself supports both Basic Authentication and OAuth. Microsoft's documentation also notes that most modern clients, including Outlook, do not use SMTP AUTH to send mail. A successful Outlook test cannot validate the copier's setup. See Microsoft's SMTP AUTH explanation.

Use evidence to confirm the inventory

An authorized administrator can review the SMTP AUTH Clients report in the Exchange admin center under Reports and Mail Flow. It identifies sender addresses and whether the reported authentication protocol is Basic Auth or Modern Auth. Its default view covers seven days; Microsoft documents date ranges up to 90 days. See the report documentation.

Use that evidence alongside staff interviews and device settings. A report that runs only at quarter-end may not appear in a short observation window. Mark unexplained sending accounts for investigation rather than assuming an empty report proves that every workflow is ready.

Choose the replacement around the business requirement

Ask the device or software vendor whether the exact model, firmware, and application version support a suitable modern-authentication option. Get the answer in writing before buying hardware or scheduling a cutover.

Microsoft documents several sending methods with different requirements. For example, Direct Send does not relay messages to external recipients, while SMTP relay requires an appropriate connector and certificate or qualifying static public IP configuration. A method that works for scans to employees may not work for documents sent to customers. Review Microsoft's device and application sending guide.

Have IT evaluate the security and support implications of the selected method. Avoid a blanket change that weakens tenant protections simply to keep one undocumented device working.

Test the real workflow before retiring the old one

Pilot one device or application first. Use a harmless test document and confirm delivery to each recipient type the workflow genuinely needs. Check the sender identity, attachment, destination inbox, and any failure notification. Then ask the staff member who uses the process to repeat it.

Record the result, change owner, support contact, and approved fallback. Include an ordinary operating cycle after the change, not just a single test message. Where a temporary exception is necessary, give it a responsible owner and a review date.

The useful outcome is a list of working, supported sending workflows. October is a good time to start that work while there is room to coordinate vendors and test without a year-end rush.
